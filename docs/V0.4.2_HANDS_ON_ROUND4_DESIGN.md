# v0.4.2 Hands-on Round 4 — frozen design

## Purpose

Round 4 turns the real-user hands-on feedback from the completed Round 3 candidate into a denser placement surface, a Voice-centered expression workflow, safer Settings ergonomics, and an experimental generic expression-preset source.

Frozen product base:

- parent Draft PR: **#15**
- parent branch: `work/v0.4.2-hands-on-round3-prep`
- exact source HEAD: `fdc3f3e5448cdf5ce7c9498776362b1bf598c2b1`
- exact source/tested tree: `3aa91dd12a8262e60c1909293fb68f93a0a032d1`

Round 3 stays Draft/open/unmerged. Round 4 is a child; do not rewrite the Round 3 evidence chain.

Product direction:

> **remove low-value chrome, keep spatial memory global, treat one Voice as one operation context, and let YMM4/tachie plugins translate their own expression presets when possible**

Do not redesign the placement core, Timeline/Preview navigation coordinator, Template fidelity model, or native Undo architecture.

## 1. Compact normal placement surface

### 1.1 Generic header

The Generic placement header becomes compact:

```text
汎用・時間位置                         レイヤー 8 ▾
再生位置に、テンプレートの長さで配置
```

The exact spacing is responsive; the semantic layout is fixed:

- context title/detail stay on the left;
- a compact Generic layer affordance stays on the right;
- the existing full-width Generic layer block is removed from the normal surface.

The layer affordance is shown only for Generic placement.

### 1.2 Generic layer popup

Left-click opens a small bounded popup/flyout containing the existing Generic target behavior:

- numeric target layer;
- 配置しない;
- 上の空きを探す;
- 下の空きを探す;
- saved bounds hint.

Reuse `GenericLayerTargetDraft`, `LayerSearchMode`, `QuickDropPlanner` and `LayerPlanner`. Do not add another planner.

Preserve:

- Enter = apply a clean numeric draft;
- Esc = restore saved target;
- free target wins exactly;
- search only when occupied;
- 上 = smaller layer number;
- 下 = larger layer number;
- no opposite wrap.

The primary left-click must open and stay open. Do not reproduce the Round 3 ContextMenu open/close competition.

### 1.3 Remove placement-surface Set全体

The top-level `Set全体 ▾` button is removed from the normal placement surface.

Its useful actions move to Settings:

- Set-wide shape;
- detailed current-Set settings.

The bottom-right Settings button becomes context-aware:

- if a current Set exists, open Settings with the current context and current Set already selected;
- if no current Set exists, open the normal context landing.

The tile context menu may retain a direct “Setの設定を開く” shortcut because it adds no permanent chrome.

The old left-click Set全体 flash-close bug is therefore removed with the obsolete surface.

## 2. Global presentation contract

Round 3 already stores presentation globally in `PlacerSettings.Presentation`. Round 4 must make the UI match that model.

### 2.1 Global, never per Set

These remain one global contract across every Set/context:

- Auto / Fixed layout;
- Fixed column count;
- position shortcuts;
- expression viewport-follow mode.

Switching Sets must never change those values.

The same physical slot therefore keeps the same shortcut meaning across Sets.

### 2.2 Settings ownership

`PalettePresentationPanel` moves to a clearly top-level “全体の表示・操作” area, outside the selected Set editor.

No presentation field is copied into a Generic or targeted Set model.

### 2.3 Expression row height

Add one global bounded expression-list row-height setting:

- default: **36**
- minimum: **32**
- maximum: **96**

The Voice grid keeps one common height for all rows.

Serif text:

- keeps the current font size;
- uses wrapping;
- may show multiple lines as row height grows;
- still clips/trims overflow inside the fixed row height;
- never auto-expands each row to full text.

Do not shrink text to force a whole Serif into the current row.

Expose a compact row-height control where the user can see the expression list while adjusting it. Persist the final bounded value through the normal settings store.

## 3. Voice operation is one authoritative action

The existing authoritative row route remains:

`CloseExpressionTrialSession -> CurrentFrame -> Select Voice -> bounded Preview SeekAsync -> viewport follow`.

### 3.1 Dropdown-open navigation

Opening the expression ComboBox for a row invokes the **same** `NavigateExpressionRowCommand` used by row click.

No duplicate ComboBox seek logic.

Rules:

- `DropDownOpened` forwards the row to the common command;
- do not consume/close the ComboBox event;
- opening and then cancelling may leave the Timeline at that Voice;
- keyboard-open and mouse-open have the same semantics;
- the row click guard still prevents a second row-click route from the interactive ComboBox.

Resulting user model:

```text
Voiceを操作する
 -> Voiceへ移動
 -> 字幕確認
 -> 表情を選択/反映
 -> その場で表情確認
```

### 3.2 Preview after immediate mutation

After a successful immediate expression replacement for the currently operated row, Preview confirmation must use the same latest-wins navigation coordinator.

If a same-frame refresh is needed, requeue the same authoritative row navigation. Do not add a second Preview adapter or direct View-side SeekAsync call.

## 4. Voice list readability

Column width remains user-adjustable through the DataGrid.

Round 4 adds the global row-height control from section 2.3.

The selected Serif detail/tooltip remain secondary aids; they are not a substitute for readable multi-line rows.

## 5. Settings: remove Save as a user concept

The user-facing need is:

> “今回設定したけど、やっぱりやめた。今回の変更だけ元へ戻してほしい。”

The normal Settings footer therefore removes:

- `変更を保存`
- `変更を破棄`

and exposes:

- **`今回の変更を戻す`**

### 5.1 Internal model

Keep the existing staged `IntentSettingsSession` safety boundary. Do not replace it with uncontrolled direct mutation.

A Settings session owns three concepts:

1. **Open baseline** — immutable deep copy of settings when the session opens.
2. **Working draft** — current UI state, including temporarily invalid text.
3. **Last committed fingerprint** — latest settings state successfully persisted by this session.

### 5.2 Automatic safe commit

A valid Settings edit is committed automatically.

The root owns one coalesced commit request; no polling timer and no independent View save logic.

On an edit:

1. coalesce the burst at the root;
2. try to build/validate the complete draft;
3. compare live settings with the last committed fingerprint;
4. call the existing atomic `PlacerSettingsStore.Save`;
5. publish the new live settings;
6. refresh affected placement/expression vocabulary without resetting the current Settings navigation/selection;
7. update the last committed fingerprint.

An incomplete/invalid text draft is **not** written. It remains visible for correction and shows a local “反映待ち/入力を確認” notice.

External or competing settings changes still fail closed. Never overwrite a digest/fingerprint conflict.

### 5.3 Session rollback

`今回の変更を戻す`:

- requires that live settings still match the session’s last committed fingerprint;
- atomically writes the immutable open baseline;
- refreshes live placement/expression state;
- resets the Settings working state to that baseline;
- affects settings only, never Timeline, original YMM4 templates, or manual items.

The button is enabled when either:

- persisted settings differ from the open baseline; or
- an uncommitted invalid/incomplete draft differs from the last committed state.

### 5.4 Explicit operations

`新しい表情を取り込む` remains a separate explicit user action.

If invoked inside the same Settings session, its settings-store effect participates in `今回の変更を戻す`.

Confirmation dialogs for destructive Set removal remain.

Before leaving Settings:

- flush a valid pending commit;
- do not silently discard an invalid/incomplete draft.

## 6. Nested Settings scrolling

Fix the nested wheel contract around `テンプレートをまとめて追加`.

Desired behavior:

- wheel over the inner template list scrolls the inner list while it can move in that direction;
- when the inner list is already at the requested edge, further wheel input bubbles to the outer Settings ScrollViewer;
- wheel outside the inner list scrolls the outer Settings surface;
- dragging either scrollbar still works;
- no global unconditional `Handled=true`.

Implement one focused nested-wheel helper rather than scattered handlers.

## 7. Experimental expression-preset source

### 7.1 User surface

`表情をまとめて` gains one source switch:

```text
[ テンプレート ]  [ プリセット（実験的） ]
```

This is a global source mode for the expression workspace, not a per-row setting.

Rules:

- Tool/session starts in **Template** mode;
- Template mode keeps all current Round 3 behavior unchanged;
- Preset mode is explicitly marked experimental;
- switching source mode itself does not mutate Timeline.

### 7.2 Placement geometry in Preset mode

Preset mode creates a bare `TachieFaceItem` for the row Character.

Its position/length/layer use the existing content-independent expression placement rules:

- `ExpressionPreset`;
- `CharacterExpressionProfile.Span`;
- `LayerPlanner`.

When Preset mode is active, the existing `ExpressionPresetPanel` is the placement-range editor for this mode.

Do not invent a second duration/layer system.

Template/relative mode continues to use its current saved Intent palette geometry unchanged.

### 7.3 Generic capability detector

Do **not** maintain a third-party plugin allowlist.

Resolve only the current Character’s tachie plugin through the existing YMM4 plugin registry and exact current tachie type.

Use the current CharacterParameter as read-only context and a **fresh plugin-created FaceParameter** as the dry-run target.

The detector recognizes two primary patterns.

#### Direct named preset

Strong candidate when a coherent structure exists, for example:

- exact public writable face-side `Preset : string`;
- character-side Preset-context definitions/list;
- at least one usable candidate;
- setting a different candidate mutates the fresh FaceParameter.

#### YMM4 property-editor preset

Look only at the fresh FaceParameter’s own public properties and their attributes. No assembly-wide “Preset” scan.

A property/attribute is a preset candidate when the local structure is coherent:

- property/display/editor name has Preset context;
- editor exposes the YMM4 property-editor shape;
- tachie-aware CharacterParameter can be supplied;
- the editor can be created and bound to the fresh FaceParameter;
- candidate choices can be enumerated from the created bounded editor surface.

Support both host contracts observed in Lab:

- legacy `PropertyEditorForTachieParameterAttribute`;
- modern `PropertyEditorAttribute/2 + IPropertyEditorForTachieParameterAttribute`.

Prefer the modern/public contract where available.

### 7.4 Confidence

The detector reports:

- **Strong** — candidate enumeration plus dry-run selection causes a semantic fresh-FaceParameter mutation;
- **Experimental** — coherent Preset candidate/choices exist, but isolated dry-run cannot prove the final mutation;
- **None** — no coherent expression-preset capability.

A name such as `CompressionPreset` alone is not enough.

A broken candidate is contained locally; it must not disable Template mode or other Characters.

### 7.5 Editor hosting boundary

Some YMM4 property editors require a real WPF visual host before choices/bindings settle.

Use one bounded staging host dedicated to this capability.

The View may only provide the local visual host. Discovery, scoring, selection, fresh FaceParameter mutation and failure handling remain in a focused service/root-owned workflow.

Do not use:

- UI Automation;
- fake mouse/keyboard input;
- private fields;
- arbitrary assembly-wide reflection;
- Timeline mutation during probing.

### 7.6 Candidate identity and session cache

For each discovered candidate keep at least:

- display label;
- route kind;
- stable candidate ordinal/key where available;
- post-apply public FaceParameter state hash for Strong candidates;
- tachie/face plugin fingerprint.

Cache discovery only for the Tool session in Round 4.

Fingerprint includes at least:

- YMM4 version;
- tachie plugin runtime type;
- face-parameter runtime type;
- plugin module MVID;
- current Character/config identity or a bounded CharacterParameter fingerprint.

Do not add persistent learned-compatibility storage in Round 4.

### 7.7 Applying a preset

At actual selection time:

1. revalidate row/Voice freshness;
2. resolve the same tachie plugin;
3. create a new fresh FaceParameter;
4. apply the selected candidate again;
5. for Strong candidates, require the expected semantic state hash;
6. create a bare `TachieFaceItem` for the current Character and assign that prepared FaceParameter;
7. apply existing `ExpressionPreset` span/layer planning;
8. fully preflight replacement before mutation;
9. commit through `PlacementPlan` + native Undo.

No existing/manual Item is modified to make room.

### 7.8 Exact managed association

Preset-generated expressions need their own exact source descriptor; do not pretend they are an Intent palette entry.

Add a small versioned experimental preset association tag containing enough data to identify:

- Plugin-managed group/source;
- preset capability fingerprint;
- candidate label/key;
- prepared FaceParameter state hash.

Unify only the **managed-expression reader/removal boundary** so template-source and preset-source expressions can replace/remove each other safely.

Do not rewrite the proven template planner.

Rules:

- replacement/removal is exact association only;
- copied/missing/ambiguous managed tags fail closed;
- manual/unassociated expressions are never guessed or removed;
- a disappeared preset candidate is shown unavailable rather than silently substituted;
- native Undo/Redo remains authoritative;
- immediate trial-session semantics remain one logical Undo.

### 7.9 Source switching and unsupported secondary workflows

Switching Template <-> Preset changes the visible candidate source only.

If the currently associated expression came from the other source, show an explicit current-source/unavailable state rather than guessing a match.

Round 4 scope:

- immediate row selection/apply: supported;
- exact removal: supported;
- reopen/reconstruct from exact preset association: supported when the candidate still resolves;
- Excel import/export: **Template mode only**;
- switching to Preset mode while protected imported Excel assignments are pending is blocked;
- legacy/explicit Resync skips experimental preset associations with truthful reporting rather than partially reconstructing them.

## 8. Optional Item-type button ordering

User-custom Item-type button ordering is useful but low-frequency and explicitly non-essential.

It is **not a Round 4 release gate**.

Do not add it in the required implementation unless the required Round 4 work is already green and it can be added as a small display-order-only change with:

- stable type identity;
- explicit reorder mode;
- “標準順に戻す”;
- unknown/new types appended safely.

Otherwise leave it for a separate child round.

## 9. Compatibility principle

Host-sensitive pieces degrade independently.

Failure of experimental Preset detection must not disable:

- Template expression mode;
- normal placement;
- Voice navigation;
- Preview seek;
- viewport following;
- Settings.

YMM4 version number alone is not the detector.

## 10. Non-goals

Round 4 does not add:

- per-plugin hard-coded expression adapters as the primary design;
- a persistent compatibility database;
- a generic property/script/DSL engine;
- arbitrary reflection across loaded assemblies;
- UI Automation/fake input to choose presets;
- Preset-mode Excel schema changes;
- automatic repair of ambiguous expression associations;
- per-row independent height;
- automatic full-Serif row expansion;
- a new placement engine;
- a new Undo stack;
- Item-type button reorder as a required feature.
