The goal of v0.4.1 is not feature expansion for its own sake. It closes the remaining workflow costs found during hands-on review and the second UX audit:

1. preserve material unfinished work across the native Tool close/reopen ViewModel replacement,
2. add many YMM4 Templates to a Palette in one safe operation,
3. let the user order a Palette in the order that is useful to them,
4. make rare destructive settings operations truthful before commitment,
5. remove ambiguous discard wording,
6. disambiguate same-name choices only when needed.

---

## Goal

A Palette should behave as a personal working toolbox:

> create/open a Palette -> select several YMM4 Templates -> add them together -> arrange them in a useful order -> Quick Drop from that order -> close/reopen the Tool without unexpectedly losing material unfinished work.

The beginner path must stay obvious, while repeated work should no longer require N repetitions of the same setup action.

# A. Transient resume continuity

## Problem

Native proof established that YMM4 may keep the Tool view while replacing its `PlacerViewModel` after close/reopen. The current implementation explicitly resumes the selected Selection Template, but other material unfinished work may be lost.

The distinction is important:

- preserving unfinished work is not the same as committing effects,
- a Tool reopen must not write Timeline/settings merely to restore UI state,
- recovery must be exact; it must never guess a moved/changed target.

## Design

Add a session-only `TransientWorkSnapshot` (name may change) outside persisted `PlacerSettings`.

Lifecycle:

```text
old PlacerViewModel
    -> CaptureTransientWork()
PlacerView / Tool lifecycle keeps snapshot in memory
    -> new PlacerViewModel
    -> native Timeline/context ready
    -> RestoreTransientWork()
```

This snapshot is not written to the settings file and is not crash recovery.

## Resume candidates

Material unfinished state that SHOULD resume when its exact source is still valid:

- Expression row Template selections,
- unsaved Expression preset draft,
- unsaved Selection preset draft,
- selected Selection Template,
- selected Palette entry,
- unsaved Palette Layer draft,
- Palette rename/create draft,
- Template-add task state,
- Template-add search text,
- Template-add multi-selection,
- Template-management editing state where safe.

Do NOT resume transient success notifications. Errors/partial results keep the existing task-aware semantics. Already committed Timeline effects are not snapshot content.

## Exactness rules

Expression assignments may resume only when the original Voice can still be identified without guessing. Use the existing captured fields/identity needed to establish unchanged Voice meaning, e.g. Character, Frame, Length, Serif, Layer and existing exact source reference as applicable.

Preset drafts may resume only when their source preset ID still exists and the saved source content has not changed underneath the draft.

Palette drafts may resume only when the exact Palette still exists and the persisted values the draft was based on are unchanged.

If a target changed, skip that item rather than repairing it heuristically.

A partial resume may report concise actionable feedback such as:

> 48件の途中選択を復元しました。2件は音声が変更されているため復元していません。

Restore itself must cause zero Timeline mutation and zero settings write.

## Boundary

Guaranteed only for Tool close/reopen within the same YMM4 process. Persisting unsaved drafts across YMM4 process exit/crash is FUTURE.

# B. Bulk Palette add

## Product rule

Single add and bulk add are one operation with different batch sizes. Do not build a separate unsafe path for bulk.

Internally route both through one `Template Add Batch` planning/commit path:

```text
selected native Templates
    -> validate every source and destination
    -> build complete batch plan
    -> one settings mutation
    -> refresh candidates once
```

Batch size 1 replaces/uses the existing single-add path.

## UI

The existing `＋テンプレートを追加` task remains the entry point.

The native source list becomes multi-select in an obvious way. Prefer check-style selection over relying only on Ctrl/Shift knowledge.

Example:

```text
☑ 笑顔
☑ どや顔
☐ 困り顔
☑ 驚き

3件選択中                       選択解除
```

Search filtering must not silently clear selections that are temporarily hidden by the filter. Show the total selected count.

Do not add a separate Bulk mode/tab.

### One selected source

Keep the current optional short display-name edit.

### Multiple selected sources

Do not require per-item naming before addition.

- New `LibraryEntry`: use the native YMM4 Template name as initial display name.
- Existing exact LibraryEntry: retain its existing display name.
- User may rename later in Template Management.

Primary action should expose batch size, e.g. `12件をパレットへ追加`.

### Already in current Palette

Show as already added / unavailable for selection rather than producing an error.

### Linked Character Palette

Only compatible native Templates should be selectable:

- the linked Character,
- neutral/non-Character Template where existing semantics allow it.

Do not let the user select another Character and discover the mismatch only after the batch is built.

### First-use with no Palette

If all selected Templates have one unique same Character, derive/create that linked Character Palette.

If selected sources are mixed/neutral/no Character, create a manual Palette using the current default user-facing vocabulary. Do not reintroduce a Character/Style mode choice.

### Expression `＋表情を追加`

Reuse the same batch engine. That entry point already filters to exact-Character Face Templates, so it should allow adding several relevant expression Templates at once.

After success, return to the originating row/task and refresh candidates, but do not invent an assignment.

## Atomic preflight

Before any settings write, validate the entire batch.

Blocking examples:

- native source disappeared,
- strict source is ambiguous,
- multiple plugin registrations refer to one exact source,
- incompatible linked Character,
- destination Palette was removed/replaced,
- Expression recovery source Voice changed,
- underlying settings/state changed in a way that invalidates the plan.

If one selected item is blocking, commit none of the batch.

An existing membership is a no-op, not a fatal error.

LibraryEntry reuse must remain exact and duplicate-safe.

# C. User-controlled Palette ordering

## Data model

Do not add a new order field or order database.

`PaletteDefinition.LibraryEntryIds` already expresses Palette-local order and remains the source of truth.

## Interaction

Primary reorder interaction: drag and drop.

Quick Drop currently uses entry click/double-click, so do not make the entire item an indiscriminate drag start region. Provide a small drag handle and use a movement threshold before starting drag.

Example:

```text
⋮⋮  笑顔
⋮⋮  通常
⋮⋮  どや顔
⋮⋮  怒り
```

Show a clear insertion position while dragging.

Fallback controls in the Palette editor:

- `↑ 上へ`
- `↓ 下へ`

Do not add a dedicated Reorder mode.

## Commit semantics

A successful move immediately saves the new `LibraryEntryIds` order.

- no separate unsaved reorder draft,
- keep the same Palette entry selected after moving,
- moving an entry in one Palette must not reorder the same LibraryEntry in another Palette.

Quick Drop double-click must continue to work after adding drag support.

## Expression candidate priority

Existing candidate preference already derives priority from Palette membership order. Therefore, user reordering should naturally change the Palette-preferred order in Expression candidates. Do not add another sort system.

Placement geometry / Layer planning must remain unaffected.

# D. Rare destructive operations

Do not add a general History/Undo engine for settings in this revision.

Instead, protect only rare actions whose recovery cost is meaningful.

## Delete Palette

Before commit, show a concise consequence summary including the number of Palette entries.

Example:

> 「小夜・表情」を削除します。\n> このパレットには12件のテンプレートがあります。\n> 元テンプレート、テンプレート管理の登録、タイムラインは削除されません。

Cancel -> zero settings write.

## Unregister LibraryEntry

Precompute how many Palettes will lose membership and disclose it before commit.

Example:

> 「笑顔」を登録解除します。\n> この登録は3個のパレットからも外れます。\n> 元のYMM4テンプレートとタイムラインは削除されません。

Cancel -> zero settings write.

Removing one entry from only the current Palette remains a lightweight reversible-by-readd action and does not require the same confirmation burden unless later evidence shows otherwise.

# E. Intentional discard wording

The Template Add task currently labels its destructive exit `戻る`, while returning from secondary Template Management to the pending add task preserves the add draft.

Make the semantics truthful:

- leaving Template Add and discarding its draft -> `キャンセル`,
- returning from secondary Template Management to the pending add task -> `戻る`.

Do not make identical wording mean both preserve and discard.

---

# F. Same-name identity clarity

Do not forbid duplicate display names. Disambiguate only where collision makes a real user decision ambiguous.

## Palette selector

Normal unique name:

> 表情

Collision example:

> 表情 — 小夜
> 表情 — ミコ

For two manual Palettes with the same name, add the smallest stable user-facing differentiator necessary inside that choice list. Do not expose GUID/PathJson as normal UI.

## Expression / Template choices

Keep the compact short display name when unique. When two visible choices have the same display name, add Character/source context sufficient to distinguish them.

Use the same philosophy already proven for same-name Selection Templates: strict identity stays internal; the user gets enough nearby context to choose correctly.

---

# G. Scene refresh wording

Rename the broad global `更新` action to `シーン更新` (or an equally specific final Japanese label after native UI review).

Keep the existing consequence guidance/confirmation when refreshing would clear expression assignments.

The label should communicate that this re-reads the current scene/native Template context rather than merely repainting one view.

**Target state:** one add task handles 1/N native Templates through one atomic engine.

**Target state:** user can arrange a Palette and the order is persistent and Palette-local.

Implement:

- up/down fallback,

- selected-entry stability,
- Expression candidate priority follows Palette order,
- Quick Drop double-click regression.

## WUX11 — Safety & Intent

**Target state:** same-name choices are distinguishable without polluting normal unique-name UI.

# FUTURE / OUT

Not part of this revision:

- same-Character multi-row Expression assignment (P2 / FUTURE),
- crash recovery of unsaved drafts,
- restoring unsaved drafts after YMM4 process exit,
- general settings history/Undo,
- Palette folders/groups,
- automatic sorting rules,
- Command Palette,
- shortcut framework,
- generic rule engine,
- fuzzy recovery,
- new placement Profile families.

The ordering feature intentionally stops at **respect the user's order** rather than trying to infer a smart order.

---

# Minimal implementation surface

The intended new conceptual surface is limited to:

- transient resume snapshot,
- atomic template-add batch plan,
- Palette move operation,
- rare destructive confirmation.

Everything else should reuse current capability and storage. If implementation starts requiring a new Library store, order DB, session DB, history engine or generic drag/drop framework, stop and re-evaluate against this design before expanding scope.
