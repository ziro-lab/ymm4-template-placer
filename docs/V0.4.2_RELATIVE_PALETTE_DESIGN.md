# v0.4.2 Design — Relative Intent Palettes

## Status

Design-only revision on `feature/v0.4.2-character-template-bundles`.

This document revises the v0.4.1 interaction model. It does **not** authorize merging `main`; PR #6 stays Draft until hands-on acceptance of a later implementation Candidate.

The existing v0.4.1 safety core remains the baseline:

- YMM4 Templates remain the source of truth.
- Plugin-side storage remains reference-oriented; no copied Template database.
- Placement is add-only unless an explicit Resync operation updates an already-associated item.
- Placement is planned/preflighted before Timeline mutation.
- Existing unrelated items are never moved/shortened/deleted to make room.
- Required-plan failure produces zero partial placement.
- YMM4 native Undo/Redo remains authoritative.
- Missing/ambiguous Template references are never fuzzy-picked.

The product model above the core changes substantially.

---

# 1. Product definition

YMM4 Template Placer is a tool for reusing **editing intent expressed as relative placement**.

Video editing repeatedly starts from something the editor wants to show, then places supporting items relative to that reference.

Examples:

- Voice -> place an expression from Voice start until the next Voice of the same character.
- Video -> place a scene transition at the end of the selected Video item.
- Text -> place decoration over the same span and above the selected Text item.
- Two selected items -> place an effect at their boundary.

v0.4.2 therefore treats Palette as the reusable unit of intent:

```text
WHEN this kind of item/context is selected
+ WHAT I want to do
+ HOW supporting items relate to that context
+ WHICH concrete Templates can realize the intent
= Palette
```

Short definition:

> **Palette = a reusable bundle of “when this happens, this is what I want to do”.**

Normal editing should become:

```text
select reference item(s)
-> applicable Palettes are filtered automatically
-> switch intent tab if necessary
-> click a concrete action tile
-> placement relation is already known
```

The goal is not “fewer settings”. The goal is:

> **make the decision once during setup; do not ask the editor to make the same decision again during normal editing.**

---

# 2. Palette is editing intent, not a Template shelf

v0.4.1 largely treats a Palette as an organized list of Library entries.

v0.4.2 changes the meaning:

```text
Palette
- identity / display name
- applicability: what selected context this Palette is for
- optional Character condition
- relative placement relation
- collision escape policy
- ordered concrete Template choices
```

Examples:

```text
Palette: 表情
Applies to: VoiceItem
Character: 小夜
Relation:
  start = selected Voice start
  end = next same-Character Voice start
  fallback end = selected Voice end
  vertical relation = 上
  collision escape = further 上
Entries:
  通常 / 笑顔 / どや / 困り / 怒り
```

```text
Palette: シーンチェンジ
Applies to: Video item type
Relation:
  anchor = selected Video end
  vertical relation = 上
  collision escape = further 上
Entries:
  フェード / 押し出し / ワイプ / 暗転
```

The Palette name describes the **editor's intent**. Entries describe the concrete variant.

A concrete entry should not normally ask the editor to choose placement rules again.

# 3. Context-first Palette filtering

## 3.1 Item type is the first filter

The primary Palette applicability condition is the selected YMM4 Item's runtime type.

Conceptually:

```text
selected Voice item
-> show Voice-compatible Palettes

selected Video item
-> show Video-compatible Palettes

selected Text item
-> show Text-compatible Palettes
```

Do not show every Palette and require the user to manually hunt for the relevant one.

The selection itself creates the editing context.

## 3.2 Persist a type key, not a closed product enum

YMM4 and YMM4 plugins can expose additional Item implementations. The design should not require a new Template Placer release merely to represent every possible Item class.

Use a persisted Item type key derived from the live Item runtime type, subject to native compatibility proof. Prefer a stable type identity such as full type name plus the minimum assembly discriminator required to avoid collisions.

If a previously configured type is unavailable after a YMM4/plugin change:

- keep the Palette in Settings,
- mark its target type unavailable,
- hide it from normal editing,
- never silently reinterpret it as another type.

## 3.3 Additional context filters

After Item type, a Palette may add a small finite set of context conditions.

Initial supported conditions should be limited to practical editing semantics, for example:

- CharacterName equals selected item CharacterName.
- single / pair / multi-selection cardinality.
- all selected items are the same type.
- selected pair provides an agreed boundary.

Do not expose an arbitrary boolean expression language.

# 4. Character semantics and first setup

## 4.1 User-facing Character identity

The current implementation mixes two different meanings:

- Palette Character association is largely `CharacterName` based.
- Expression candidate matching can require YMM4 `Character` object equality.

This creates the visible failure where a Template can be added to a Character Palette but does not appear as a Voice expression candidate.

v0.4.2 uses **CharacterName as the user-facing logical Character key** for Palette applicability and expression candidate grouping.

Template source resolution itself remains strict by TemplateLocator. Character grouping is not permission to fuzzy-resolve a missing Template.

If multiple host Character objects share the same displayed CharacterName, they intentionally belong to the same logical editing Character for Palette filtering. Settings may report that multiple host Character objects share the name, but expression visibility must not depend on reference identity alone.

## 4.2 Bootstrap from Templates, not from existing settings

On first v0.4.2 setup, scan live YMM4 Templates.

For every CharacterName represented by a Template containing at least one `TachieFaceItem`:

1. Create the initial Character expression Palette automatically.
2. Use the CharacterName as the default Palette name.
3. Add the matching live Templates in deterministic order.
4. Do this once as bootstrap; after setup, normal Template changes do not silently rewrite user Palette membership/order.

This makes first-use setup subtraction-oriented:

```text
all useful expression Templates are already present
-> remove unwanted entries
-> reorder the remaining entries
```

rather than asking the user to discover and add every expression manually.

## 4.3 Template eligibility for Character bootstrap

A Template is eligible for Character bootstrap when:

- it contains at least one `TachieFaceItem`, and
- all Character-bearing items that participate in that Template resolve to one CharacterName.

A Template containing multiple different CharacterNames must not be auto-assigned to one Character Palette. Keep it available for explicit manual configuration instead.

A multi-item Template that contains an eligible Face item is still a Template bundle; do not discard it merely because it contains more than one item.

## 4.4 Multiple Palettes for the same Character

Allow multiple Palettes with the same Character applicability.

Default naming:

```text
小夜
小夜 2
小夜 3
```

The first auto-created Palette gets the plain CharacterName. Later Palettes may be renamed freely.

Character identity and Palette identity are separate. CharacterName filters applicability; Palette name describes the editor's reusable intent/set.

# 5. Relative relationship model

The important flexibility is not arbitrary coordinates. It is the ability to describe useful **relationships**.

A Palette relation is composed from a finite set of primitives.

## 5.1 Reference selection

The primary reference is normally the selected item or selected set.

Supported anchors should include at least:

```text
selected start
selected end
selected center
selected range start
selected range end
pair boundary
```

## 5.2 Neighbor lookup

A Palette may inspect a related item around the reference.

Initial finite neighbor queries:

```text
previous item of same Item type
next item of same Item type
previous item with same CharacterName
next item with same CharacterName
previous item of same type + same CharacterName
next item of same type + same CharacterName
```

Each query is deterministic and directional. Do not search by fuzzy text similarity, nearest-looking item or arbitrary property expressions.

## 5.3 Time relation

Initial time relations should cover common editing needs:

```text
use Template intrinsic duration
match selected item span
start at selected anchor + offset
end at selected anchor + offset
end at related-neighbor anchor + offset
fixed duration from an anchor
cover selected range + padding
```

Example Character expression:

```text
start = selected Voice start
end = next same-Character Voice start
fallback if no next same-Character Voice = selected Voice end
```

Fallback behavior is explicit per Palette. Missing relation targets are never guessed.

## 5.4 Layer relation uses 上 / 下

Normal UI terminology must be:

```text
上 = smaller Layer number
下 = larger Layer number
```

Do not require users to translate “Front / Back” or “greater / smaller number” during normal work.

Initial relations:

```text
上
下
同じLayer（only where safe/useful）
relative offset N from the reference layer/band
```

For selected sets or Template bundles, the reference may use the minimum/maximum occupied layer as defined by the Palette relation.

## 5.5 Collision escape is part of the relation

A requested relative position is the first candidate, not an immediate failure.

Example:

```text
relation = 上
first candidate is occupied
-> continue further 上
-> continue in the same direction until the configured search boundary
-> fail only when no valid placement exists
```

Likewise for 下.

Never wrap around to the opposite direction unless a future Palette explicitly defines that behavior. Existing Timeline items are never moved to make room.

## 5.6 No “use Template layer” option in relative Palette operation

For context-relative editing, “use the Template's original absolute Layer” does not express the editor's intent. Placing the raw Template directly already provides that behavior elsewhere.

Relative Palette setup should ask for the relation to the selected reference (`上`, `下`, etc.), not whether to reuse an absolute source Layer.

Template internal Layer differences remain meaningful for multi-item bundles; the bundle as a whole is translated relative to the target.

# 6. Multi-item Template bundles

v0.4.1 rejects Templates unless they contain exactly one item in the plugin Library/placement path. v0.4.2 explicitly revises this boundary.

## 6.1 Template bundle definition

A YMM4 ItemTemplate with N items is one placement bundle.

When placed:

- clone every item independently,
- preserve each item's relative Frame offset inside the Template,
- preserve relative Layer offsets inside the Template,
- translate the bundle as a unit to satisfy the Palette relation,
- do not flatten the bundle into unrelated independent placement decisions.

## 6.2 Bundle origin

Define a deterministic source geometry origin from the Template, for example:

```text
frame origin = minimum source Frame
layer origin = relation-specific source layer baseline
```

The exact layer baseline must be native-proved before implementation; the important contract is that internal relative Layer differences are preserved.

## 6.3 Bundle collision search

Collision escape chooses one common Layer translation for the whole bundle.

For a candidate layer shift `delta`:

```text
for every cloned bundle item:
  check its own Frame span
  check translated Layer
against:
  all existing Timeline items
  all items already reserved by this plan
```

Only if **all** items are valid is that shift accepted.

If the Palette says 上, try progressively smaller common Layer shifts. If 下, progressively larger shifts.

No partial bundle commit.

## 6.4 Group metadata

YMM4 `Group` semantics must not be guessed. A Template bundle is a Template Placer planning unit even if native Group IDs cannot safely be reproduced across scenes.

Preserve/recreate native grouping only if native proof demonstrates that it is safe and portable. Otherwise placement atomicity comes from one PlacementPlan / one Undo operation, not invented Group IDs.

# 7. Normal editing UI

## 7.1 Selection drives the surface

Normal editing should not begin with Library management.

When selection changes:

1. determine current Item type/context,
2. filter applicable Palettes,
3. display only those Palettes,
4. retain a valid last-used Palette for that context when possible.

No applicable Palette:

```text
「この種類のアイテム用のパレットはまだありません」
[設定を開く]
```

Do not show irrelevant Palettes as disabled noise.

## 7.2 Palette switcher should be tabs

A Palette is an editing intent frequently switched during work. A hidden dropdown is therefore the wrong primary interaction.

Use tabs (or equivalent always-visible segmented navigation) for the small set of Palettes applicable to the current context.

Example Voice context:

```text
[表情] [リアクション] [字幕]
```

Example Video context:

```text
[シーンチェンジ] [強調] [終了演出]
```

Selecting another Item type immediately changes the available tabs.

## 7.3 Palette entries should be tiles/buttons

The current vertical list displays too few choices for a high-frequency action surface.

Use a wrapping tile/button layout:

```text
[通常] [笑顔] [どや] [困り] [怒り]
[驚き] [泣き] [汗]   [赤面]
```

The layout should consume horizontal width before requiring vertical scrolling.

Normal action tiles are executable actions. The intended path is single-click placement, subject to native usability proof and protection against accidental drag/reorder modes.

Reorder/delete/edit belong in Settings, not in the normal high-frequency action surface.

## 7.4 Target interaction budget

After setup, the common path should require no repeated configuration decisions:

```text
1. select target item
2. switch Palette tab if the desired intent is not already active
3. click concrete action tile
```

If the desired Palette is already active, normal placement is target selection + one click.

# 8. Settings UI

Palette construction/editing is a low-frequency setup task and should be isolated from normal editing.

Settings must support:

- target Item type selection from currently known YMM4 Item types,
- optional CharacterName condition,
- Palette name / ordering,
- relative time relation,
- neighbor query,
- 上 / 下 layer relation,
- same-direction collision escape/search boundary,
- Template entry membership,
- multi-item Template bundle visibility,
- entry reorder/delete,
- duplicate/copy Palette,
- explicit Template rescan/import.

Do not show internal resolver IDs, raw GUIDs or low-level type metadata unless needed for diagnostics.

The setup UI should use plain editing language such as:

```text
対象: ボイス
開始: 選択アイテムの開始
終了: 次の同キャラの開始
なければ: 選択アイテムの終了
配置: 上
塞がっていたら: さらに上へ
```

not a generic node/condition editor.

# 9. Expression list integration

The existing Voice Expression list remains useful as a secondary bulk workflow, but it must use the same Palette model.

## 9.1 Candidate source

For each Voice row:

1. obtain the Voice CharacterName,
2. find applicable Character expression Palettes,
3. expose their ordered entries as expression candidates,
4. do not independently rebuild a second incompatible Character rule.

Adding/removing/reordering a Character expression Palette must therefore be reflected in Voice expression candidate availability/order.

## 9.2 Multiple expression Palettes for one Character

When one Character has multiple expression Palettes, the bulk list may expose the union in Palette order, with collision-only Palette context in the display label when identical short names would otherwise be ambiguous.

Do not require a hidden `Character` object reference equality in addition to the visible logical CharacterName.

## 9.3 Multi-item expression bundles

General bundle placement and Character expression association/resync are separate concerns.

v0.4.2 should first make multi-item Templates valid Palette placement bundles. Extending Voice association/Resync to a bundle of multiple generated items requires explicit proof of:

- one Voice source -> multiple generated items,
- association identity for every generated member,
- selection-scoped Resync,
- one Undo unit,
- zero partial update on invalid bundle geometry.

Do not silently treat a multi-item expression bundle as a single `TachieFaceItem` until that proof exists.

# 10. Selection Placement consolidation

The current Selection Placement screen exposes Profile/Preset choice independently from Palette membership and can show all Library entries. This no longer matches the product model.

v0.4.2 direction:

```text
selection establishes context
-> context filters Palettes
-> Palette chooses editing intent + relation
-> Palette entries choose the concrete Template/bundle
```

Therefore:

- Selection Placement must not show the entire Library as its normal Template picker.
- Low-level Profile selection must not be a repeated normal-work decision when the same relation has already been saved into a Palette.
- Existing Profile implementations may remain internal strategies during migration, but normal UI should increasingly be driven by Palette intent.

Target Companion / Point / Range / Boundary can survive as internal relation strategies where useful. They are no longer the primary user-facing taxonomy.

# 11. Data model direction

Conceptual model; exact serialization names are implementation details.

```text
IntentPalette
- Id
- Name
- TargetContext
  - ItemTypeKey
  - SelectionCardinality
  - CharacterName? / CharacterPolicy?
- Relation
  - StartReference
  - EndReference / DurationPolicy
  - NeighborQuery?
  - MissingNeighborFallback
  - FrameOffsets
  - LayerRelation (Up / Down / Same / Offset)
  - CollisionSearchDirection
  - LayerSearchBounds
- Entries[]
  - LibraryEntryId
  - Order
```

Keep `LibraryEntry` as the strict reference to a live YMM4 Template.

Revise `TemplateResolver` from “exactly one Template item” to “resolve an exact Template and expose its item bundle”. Single-item convenience APIs may remain for legacy code during migration.

Avoid storing copied serialized Item bodies.

---

# 12. Migration from v0.4.1

Do not pretend the old `Character / Style Palette + Selection Preset` structure is semantically identical to an IntentPalette.

Migration must be conservative.

Recommended approach:

1. introduce a new settings schema with explicit IntentPalettes,
2. preserve the original v0.4.1 settings until migration is successfully saved,
3. bootstrap Character expression Palettes from live YMM4 Templates on first v0.4.2 setup,
4. offer existing v0.4.1 Palette membership as migration material rather than silently assigning invented target Item types/relations,
5. never delete old settings automatically on failed migration.

Because v0.4.1 is still Candidate, exact compatibility cost may be lower than for a public stable release, but user-created settings still deserve lossless handling.

# 13. Rule-engine boundary

v0.4.2 needs more relational freedom than v0.4.1 but must not become a generic programming language.

IN:

- finite Item type filter,
- optional CharacterName filter,
- selection cardinality,
- finite anchors,
- finite previous/next neighbor queries,
- finite same-type / same-Character neighbor filters,
- offsets/padding/fixed duration,
- 上 / 下 / limited relative Layer operations,
- one-direction collision search,
- explicit fallback when neighbor is missing,
- Template bundle translation.

OUT:

- arbitrary property reflection exposed to users,
- arbitrary AND/OR expression trees,
- scripts/DSL,
- user-entered code,
- fuzzy Template or target matching,
- hidden auto-classification from Template names,
- continuous Timeline rule execution,
- automatic movement/deletion of unrelated items.

The test for a new relation primitive is:

> Is this a common, understandable video-editing relationship that can be named directly in the UI?

If not, it should not enter the first relation model.

---

# 14. Implementation architecture

Reuse the existing safe placement core.

Desired flow:

```text
Timeline selection
-> SelectionContext snapshot
-> filter IntentPalettes
-> choose Palette
-> choose PaletteEntry
-> strict TemplateResolver resolves 1..N source items
-> RelationResolver computes target Frame/span + Layer relation
-> BundlePlanner clones and translates all items
-> Layer collision search reserves complete bundle geometry
-> PlacementPlan preflight
-> native Undo commit
```

`RelationResolver` must be pure/planning-oriented: no Timeline mutation.

`BundlePlanner` must plan against existing + already-planned occupancy.

`PlacementPlan` remains the only mutation gateway for normal add placement.

# 15. Acceptance requirements for the revision

A v0.4.2 implementation is not acceptable until native YMM4 proof covers at least:

1. First setup scans live Templates and creates one initial Character expression Palette for each eligible CharacterName.
2. Eligible expression Templates are initially imported without requiring one-by-one registration.
3. Later Palette editing can remove and reorder those entries without automatic re-import undoing the user's choices.
4. Same Character can have multiple Palettes with independent IDs/order and simple default names (`Name`, `Name 2`, ...).
5. Selecting a Voice item filters normal UI to Voice-compatible Palettes.
6. Selecting another Item runtime type immediately replaces those tabs with Palettes for that type.
7. CharacterName filtering further narrows Character-specific Palettes.
8. Palette switcher is visible as tabs/segments rather than hiding all intents inside one dropdown.
9. Concrete Palette actions render as wrapping tiles/buttons and support the common click-placement path.
10. Selection-relative placement never presents the entire Library as the normal action list.
11. `上` always means smaller Layer numbers; `下` always means larger Layer numbers.
12. When the first relative Layer is occupied, placement searches farther in the configured same direction before failing.
13. Failure at search bounds produces zero Timeline mutation.
14. The relative Palette UI has no “use Template absolute Layer” decision.
15. A multi-item Template can be selected as one Palette entry.
16. Multi-item placement preserves internal relative Frame/Layer geometry.
17. Bundle collision planning searches one common Layer shift and never partially places a bundle.
18. One bundle placement is one native Undo operation.
19. Voice expression candidates come from the same applicable Character expression Palettes and react to Palette membership/order changes.
20. Character expression visibility is based on logical CharacterName, not hidden object identity alone.
21. Broken/ambiguous Template references remain explicit and are never fuzzy-repaired.
22. All v0.4.1 unrelated-item preservation, add-only, Preflight, native Undo and package regression gates remain green.

---

# 16. Design success criterion

A user who has completed setup should be able to edit primarily by:

```text
select the thing they care about
-> see only relevant editing-intent Palettes
-> switch intent
-> click the concrete action
```

The tool should remember the relational decisions that would otherwise be repeated:

```text
where does it start?
where does it end?
which neighboring item matters?
is it above or below?
what happens if that layer is occupied?
which concrete Templates belong to this editing intent?
```

If normal editing still repeatedly asks those questions, the v0.4.2 design has not achieved its purpose.
