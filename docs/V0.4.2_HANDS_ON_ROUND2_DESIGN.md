## 1. Product direction

The common editing model becomes:

```text
Pointer context
  -> Set
  -> concrete tile
  -> one click to place
```

User-facing "Set" is the unit that answers **what do I want to do here?**. The separate normal-UI "やりたいこと / Intent" level is removed because the Set name already carries that meaning.

Examples:

- 表情
- 強調
- テロップ
- 画像装飾
- 汎用SE

The product should feel like a **context palette**, not a rule-engine editor.

## 2. UI unification, not core unification

Round 2 deliberately keeps two proven placement backends behind one presentation model.

### Item-context Set

Backend: existing `IntentPalette` + `IntentExecutionPlan`.

Used when the user pointer-clicks a Timeline Item and a non-empty selection exists after YMM4 processes that click.

The normal UI shows `IntentPalette.Name` as the Set name. Existing `IntentPalette.Intent` remains serialized compatibility metadata and is not exposed as a separate common-path navigation level.

Existing Intent strings are preserved byte/meaning-wise. New targeted Sets receive a bounded internal compatibility value automatically; the user is not asked to name both an Intent and a Set.

### Generic Set

Backend: existing `PaletteDefinition` with `PaletteKind.Style` + existing `QuickDropPlanner`.

Used when the user pointer-clicks Timeline background or the ruler/time scale.

This is intentionally **not** implemented by inventing a selection-less relative-placement profile. Quick Drop already has the correct CurrentFrame semantics and native Undo path.

### Presentation adapter

Add a small root-owned adapter model so both backends render as:

- Set choice
- tile list
- tile execute
- tile appearance/edit affordances

The adapter may delegate to different planners. It must not duplicate placement geometry or bypass the existing planners.

## 3. Context state machine

Use an explicit root state, not `CurrentFrameChanged` heuristics.

Suggested states:

```text
PlacementContext.Generic
PlacementContext.Selection
```

Transitions:

| Input | Result |
| --- | --- |
| Pointer route hits known Timeline Item route, then selection count > 0 | Selection |
| Pointer route hits known Timeline Item route, then selection count == 0 | keep current context |
| Pointer route hits known Timeline background | Generic |
| Pointer route hits known ruler / TimelineScale | Generic |
| Selection changes with no recognized pointer intent | Selection fallback when count > 0 |
| Keyboard-only CurrentFrame movement | keep current context |
| Playback CurrentFrame movement | keep current context |
| Programmatic CurrentFrame movement | keep current context |
| Unknown pointer route | keep current context |

Initial Tool/scene activation:

- if a current non-empty selection exists, begin in Selection context;
- otherwise begin in Generic context.

Scene replacement reinitializes the context by the same rule.

## 4. Input classification contract

Pinned-host Round 2 public-lab evidence proves:

- Item click route: `TimelineItemView`
- blank Timeline route: TimelineViewModel-backed Grid
- ruler route: TimelineScaleViewModel-backed visual
- re-clicking an already selected Item re-fires Timeline selection notifications
- blank clicks retain existing Item selection while moving CurrentFrame
- keyboard and playback also move CurrentFrame

Production therefore listens to public WPF input plumbing and classifies **pointer origin first**.

Recommended shape:

```text
InputManager.PreProcessInput / routed PreviewMouseDown
    -> bounded known-route classifier
    -> root coordinator records one pending pointer intent
    -> YMM4 updates selection
    -> root consumes pending Item intent on selection notification
```

Views may forward input intent but must not directly switch sibling UI state or mutate Timeline.

YMM4 visual-tree type/data-context names are version-specific. Classification must be bounded to the observed host structures and fail safe. Do not use arbitrary reflection to hunt for equivalent controls.

## 5. Set-first Settings

Normal Settings becomes:

```text
[汎用] [ボイス] [テキスト] [画像] [図形] [...]
        ->
      Set一覧
        ->
      Set詳細
```

Rules:

- remove the separate Intent selector from the common path;
- the selected Item/type is directly visible as buttons/segments rather than hidden in a ComboBox;
- frequently used built-in Item types are direct buttons;
- uncommon/plugin-defined types may live under `その他`;
- multi-type target editing remains Advanced;
- bulk Set management stays secondary inside Settings;
- legacy compatibility data stays intact.

For targeted Sets, filtering is by target context only, not by a second user-selected Intent string.

For Generic, the screen edits Style Palette Sets through the same visible Set vocabulary.

## 6. "どう置く？" structured sentence editor

The existing natural-language relation summary becomes the primary editor.

This is **not free-form NLP** and does not parse arbitrary Japanese. It is a deterministic finite grammar backed by existing enums/parameters.

Example targeted Set:

```text
[このボイスの開始] から
[次の同じキャラのボイスの開始] まで、
[上] の空いているレイヤーへ配置。
見つからなければ [現在のボイスの終了] まで。
```

The bracketed pieces are bounded selectors.

Targeted grammar maps to the existing:

- Anchor
- Duration
- Alignment
- Neighbor
- NeighborEdge
- Fallback
- RelativeLayerDirection

Only combinations valid for the current mode are offered.

Detailed numeric tuning is collapsed under `細かく調整`:

- StartOffset / EndOffset
- FixedDuration
- MaximumNeighborGap
- BoundaryTolerance
- relative layer offset/range

Generic Style/Quick-Drop Sets use a smaller grammar matching the existing backend, e.g. CurrentFrame + intrinsic template duration + saved layer policy. Do not pretend Generic has target-relative semantics it does not possess.

The summary and the editor must be one source of truth: changing a selector immediately changes the sentence preview; saving writes the same finite model.

## 7. Tile interaction model

One tile has three primary gestures:

- **left click** -> execute placement
- **left drag past WPF drag threshold** -> reorder
- **right click** -> edit tile appearance / open Set settings

Remove dependence on a narrow drag handle after whole-tile drag proves safe.

A drag gesture must suppress placement exactly once; a click below the drag threshold must remain a normal one-step placement.

Right-click common commands:

- 表示名を変更
- 色
- 形
- Setの設定を開く

Finite shapes:

- 角丸
- 四角
- 丸

No free-form corner-radius/style editor.

### Appearance storage

Targeted `IntentEntry` already stores alias/color; add a finite shape value with a backward-compatible default.

Generic Style Palette keeps `LibraryEntryIds` as the authoritative order. If per-tile generic alias/color/shape is implemented, add a small optional appearance map keyed by LibraryEntryId on that Palette rather than replacing the list or migrating to a second ordering store.

Old files missing the new appearance fields/maps must load to neutral/default appearance without rewriting on load. Do not bump a revision merely for an additive defaulted appearance property unless compatibility testing proves it necessary.

## 8. Expression specialist cleanup

Keep the proven immediate apply/replace/remove engine.

Round 2 changes only the common interaction:

- Voice row **single click** navigates to/selects that Voice;
- double-click is no longer required;
- ComboBox change remains immediate apply;
- `配置しない` remains immediate exact associated-bundle removal;
- normal list refresh still reconstructs from exact association identity.

`表情を配置` is not a normal always-visible action after immediate apply. Show it only when there is an actual pending imported/batch assignment that still needs commit.

`選択した表情を再同期` remains a maintenance operation but moves out of the main action row, for example into a `…` menu or secondary maintenance surface.

Single-click navigation must not swallow ComboBox interaction.

## 9. Preview refresh boundary

Round 2 public-lab search found no dedicated supported public Plugin API meaning "force current preview redraw".

Therefore:

- continue to use supported `Timeline.CurrentFrame` and selection navigation;
- do not use `TimelineViewModel.ScrollFrame` as a fake seek/refresh;
- do not add internal/private preview reflection, UI Automation hacks, render-helper misuse, or repeated frame toggling;
- acceptance may prove CurrentFrame/selection navigation, but must **not claim pixel-level preview refresh**.

If a future YMM4 public API appears, it can be added behind a bounded host adapter later.

## 10. Dirty-draft policy

The Round 1 global rule `IntentSettings.HasChanges => block expression actions` is too broad for hands-on use.

Round 2 separates **Timeline execution admission** from **settings mutation admission**.

### Timeline actions

An unrelated dirty Settings draft must not block:

- expression immediate apply
- expression replacement
- `配置しない`
- ordinary placement whose saved Set/source is unaffected

Block only when the pending draft changes data that the requested operation actually depends on, such as the exact Set, its membership/relation, or the referenced source.

Provide a targeted reason, e.g. "この表情Setに未保存の変更があります".

### Settings-mutating surface actions

Reorder / alias / color / shape changes persist settings. While any staged Settings draft is dirty, these direct-persist operations may remain blocked rather than silently merging two writers. The disabled reason must state that the Settings draft must be saved/discarded first.

This distinction avoids an unsafe general merge engine while fixing the actual editing interruption.

### Association serial

Do not require a user-settings write merely to trial an expression.

Association IDs are interpreted within the current Timeline and the allocator already observes existing Timeline tags. Round 2 should move immediate-trial high-water tracking to root/session state (seeded by the existing compatibility value and observed tags), so unrelated staged Settings do not conflict with a system-managed serial increment.

Existing serialized `NextAssociationId` remains a compatibility seed unless/until a later migration is separately justified.

## 12. Preserved safety core

Round 2 must not rewrite or weaken:

- live `ItemSettings.Default.Templates` source of truth
- strict `TemplateLocator`
- TemplateBundle cloning/validation
- IntentRelationResolver for targeted relative placement
- complete collision/preflight before mutation
- PlacementPlan native Undo gateway
- canonical Character rebind
- TachieFace parameter/effect fidelity
- exact association identity
- whole-bundle expression replace/remove
- explicit Resync semantics
- Excel validation/import zero-write
- protected settings save
- stable `.ymme` root `Ymm4TemplatePlacer/`

Normal targeted placement stays add-only. Expression specialist removal/replacement remains the only bounded destructive exception.

## 13. Explicit non-goals

Do not add in Round 2:

- free-form natural-language parsing
- LLM/API dependency
- generic rule engine / DSL / node graph
- new custom Undo stack
- preview private/reflection hacks
- CurrentFrame polling
- context switch on every CurrentFrameChanged
- fuzzy host visual-tree guessing
- automatic deletion/rebuild of unrelated items
- schema rewrite solely to make Generic and targeted Sets share one persisted type
- removal of legacy compatibility fields just because the common UI hides them

The goal is a smaller user model over proven internals, not a larger engine.
