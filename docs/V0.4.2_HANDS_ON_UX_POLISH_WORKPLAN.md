# v0.4.2 Hands-on UX polish — implementation workplan

Status: implementation preparation. Product baseline is the native-verified PR #11 head `eeb465438a75508a936180543ee517bdfbf292a4`. This work must not merge `main`; PR #11 and PR #6 remain Draft until new hands-on acceptance.

## Goal

The placement core now behaves close to the user's editing model. The remaining quality gap is mainly setup/organization UX. Preserve the proven placement/reference/bundle/Character/Undo cores and make the product read as three clear tasks:

- **配置** — select an Item, choose what to do, optionally switch Set, click a concrete action tile.
- **表情をまとめて** — rapidly assign/review expressions across many Voice items while looking at the YMM4 preview.
- **設定** — start from the target Item and the edit the user wants, then configure the Set; do not expose engine taxonomy first.

The governing question for every control is: **is this display/decision needed for the edit the user is trying to perform now?** A decision saved in setup must not be requested again in ordinary editing.

## Frozen user feedback

1. Rename the normal top tab `編集` -> `配置`.
2. Normal tiles must not repeat hierarchy already visible in context. `小夜/表情/うれしい` should normally display as `うれしい`.
3. Each entry may have a Template-Placer-only display alias. Never rename the live YMM4 Template for this purpose.
4. Tiles should be uniform near-square cells in a regular grid, with readable wrapping/ellipsis rather than width determined by name length.
5. Reorder tiles directly on the placement surface by drag. Preserve a non-drag fallback. A drag must never accidentally execute placement.
6. Allow a small persistent color label/preset per tile for recognition. Color is appearance metadata, not placement semantics.
7. Settings becomes **Item -> intent -> Set -> details** rather than Set -> target/type parameters.
8. Built-in Item names must be Japanese/user-facing; raw CLR names such as `TransitionItem` / `FrameBufferItem` must not leak into normal Settings.
9. Optional bulk Set management belongs inside Settings as a secondary management view, not as another top-level product task.
10. `表情をまとめて` remains a specialist high-throughput expression-placement mode, not a generic batch editor.
11. Voice-row double-click moves YMM4's preview/current frame to that Voice (and may select the Voice if a proved public API supports it). Do not auto-play by default.
12. Selecting an expression in a row should apply immediately. Selecting another expression for the same Voice replaces only the Plugin-managed associated bundle; it must not stack duplicates.
13. `— 配置しない —` removes only the Plugin-managed expression bundle for that Voice.
14. Replacement is whole-bundle and atomic: strict resolve -> clone -> canonical Character rebind -> relation/collision preflight -> association validation -> commit. Failure leaves the old expression intact and the UI returns to the actual Timeline state.
15. Rapid trial switching is preview/choice work. The user does not want one Undo entry per trial candidate. Do not implement this by inventing a custom undo stack or bypassing proven host safety; first prove an acceptable native host mechanism.
16. Investigate moving `YMM4 Template Placer` from the top Tool list into `ツール > ユーティリティ`. Implement only if the pinned host exposes a supported plugin/category surface; otherwise report BLOCKED and keep the current placement.

## Non-negotiable preserved core

Do not rewrite `IntentRelationResolver`, bundle planning, strict `TemplateLocator`, `PlacementPlan`, canonical Character rebinding, Template fidelity, protected settings save, association identity, whole-bundle Resync, Excel validation, or package/install safety merely to implement this UX pass.

Normal placement remains add-only. The only planned destructive operation is the explicit expression-row replacement/removal of an already-associated Plugin-managed bundle after complete preflight. Manual/unassociated items remain immutable.

## Model/storage plan

Prefer backward-compatible metadata additions rather than a schema rewrite.

- `IntentEntry`: optional user-facing alias and optional finite color key are appearance metadata. Missing values must load as defaults without rewriting old settings.
- Existing `Entries` list order remains the persisted tile order; no second ordering store.
- Derived tile label fallback is deterministic: explicit alias -> last non-empty Template name path segment -> original Template name. If two visible labels collide, disambiguate locally in UI/tooltip; do not mutate identity.
- Do not copy Template bodies into settings.
- Do not bump `IntentPaletteRevision` unless serialization/native compatibility proves an actual semantic migration is necessary. If a bump becomes necessary, migrate in memory and preserve old bytes until an explicit successful Save.

## Implementation phases

### P0 — host-surface preflight (must finish before H3/H4)

Use a public-safe lab probe against exact YMM4 4.55.1.1 to determine:

- whether `IToolPlugin` exposes supported category/group placement for `ユーティリティ`;
- the public CurrentFrame/selection APIs for row navigation;
- whether native Undo/Redo exposes transaction/group/merge/coalescing suitable for rapid expression switching;
- whether YMM4 exposes localized Item-type display names that can be reused safely.

No product implementation should guess these APIs. If an unsupported requirement has no safe public/proved route, mark it BLOCKED rather than adding arbitrary reflection or a custom undo stack.

### H1 — Item-first Settings (Priority A)

Primary touchpoints:

- `IntentSettingsViewModel.cs`
- `IntentSettingsDraft.cs`
- `IntentSettingsPanel.xaml`
- `IntentSelectionContext.cs`
- optional small user-facing Item-name resolver

Change the information architecture to:

`current/selected Item context -> intent -> Set -> Set behavior/details`

Requirements:

- selected Timeline Item is the first filter/context;
- Voice context does not begin with a large all-type checkbox matrix;
- multi-type targeting moves to Advanced/explicit special-case editing;
- preserve progressive disclosure and natural-language relation summary;
- preserve staged draft/save/discard/external-conflict behavior;
- all Settings navigation/editing remains Timeline zero-write;
- no raw runtime type keys in ordinary UI;
- Japanese/user-facing built-in Item names.

A secondary `Set一覧` / management view is allowed inside Settings only if needed for bulk rename/duplicate/delete/reorder; do not add another top-level app task merely for model management.

### H2 — Placement tile ergonomics (Priority B)

Primary touchpoints:

- `IntentPaletteModels.cs`
- `IntentWorkspaceViewModel.cs`
- `IntentPalettePanel.xaml`
- `IntentSettingsDraft.cs` / Settings editor for alias/color editing
- `PlacerView.xaml` / top-level copy

Requirements:

- `編集` -> `配置`;
- alias metadata and deterministic short-name fallback;
- uniform near-square tile layout, exact dimensions chosen from native narrow-layout evidence rather than arbitrary pixel preference;
- tile color presets with accessible text contrast and a neutral default;
- direct drag reorder on the working placement surface, preferably with a dedicated handle or drag threshold so a reorder gesture cannot execute the tile;
- persisted order uses the existing `Entries` order;
- click remains single-step execution;
- source Template, locator and placement semantics unchanged.

### H3 — expression high-throughput navigation and immediate apply (Priority C)

Primary touchpoints:

- `AssignmentRow.cs`
- `PlacerViewModel.cs`
- `PlacerView.xaml`
- `IntentExpressionPlacement.cs`
- `IntentAssociationTag.cs`
- `IntentAssociationResync.cs` only where whole-bundle identity/validation can be reused
- root coordinator for order-sensitive apply/replace admission

Requirements:

- row double-click forwards one command upward; View/code-behind must not mutate Timeline directly;
- move current frame to Voice start through a proved host API; optional Voice selection only if proved/safe;
- ComboBox selection applies immediately;
- a different selection replaces exactly the existing associated Plugin bundle for that Voice;
- `配置しない` removes exactly that bundle;
- whole-bundle atomic preflight; source/Character/effect fidelity uses the same path as normal expression placement;
- failure preserves old Timeline state and restores the row selector to actual state;
- opening/refreshing the list reconstructs current selector state from valid association identity, never by proximity/text guessing;
- hand-placed/unassociated Faces are untouched.

Because rapid choice is order-sensitive global workflow state, model the row-edit/apply lifecycle explicitly at the coordinator boundary rather than adding cross-view booleans or sibling callbacks.

### H4 — native Undo policy for trial switching (gated by P0)

User intent: intermediate trial candidates are not meaningful history; only the useful final Voice->expression result matters.

Allowed implementation order:

1. proved native transaction/group/coalescing API;
2. another proved YMM4-native semantic that yields one safe logical undo operation for a completed row edit session;
3. if neither exists, mark history suppression BLOCKED and keep the safer native behavior rather than implementing custom Undo or silent non-undo mutation.

Never clear unrelated Undo history. Never create a second custom Undo stack.

### H5 — host integration polish (Priority D)

- Implement `ツール > ユーティリティ > YMM4 Template Placer` only if P0 proves a supported host/plugin category route.
- If YMM4 provides a supported localized Item-name provider, use it. Otherwise maintain a bounded built-in Japanese map plus a non-raw fallback for plugin-defined types; do not display fully-qualified CLR identifiers in normal UI.

### H6 — integrated native acceptance / package

All retained gates stay mandatory. Add a dedicated hands-on-polish marker and manifest rather than weakening old tests.

Recommended marker: `HANDS_ON_UX_POLISH=PASS`.

Final packaging must require current evidence for this stage in addition to `TEMPLATE_FIDELITY=PASS` and `RELATIVE_UIUX=PASS`.

## Required native acceptance

At minimum prove in actual pinned YMM4:

1. top tab is `配置` and old feature taxonomy is absent from the common path;
2. alias and short-name fallback render as intended; source Template names remain unchanged;
3. uniform tile grid remains understandable at 360px and drag reorder persists without accidental placement;
4. tile colors persist and do not obscure selection/error/disabled semantics;
5. Settings begins from Item context and exposes only relevant intents/Sets before details;
6. built-in Item names are user-facing Japanese and raw CLR names are absent;
7. Settings remains progressive, summarized, draft-safe, external-conflict-safe and Timeline zero-write;
8. Voice-row double-click changes only navigation/selection state, not Timeline content;
9. expression ComboBox selection immediately creates a valid associated bundle;
10. second selection atomically replaces that bundle rather than stacking another;
11. `配置しない` removes only the associated Plugin bundle;
12. failed replacement leaves old bundle and selector intact;
13. reopen/refresh reconstructs selector state from exact association identity;
14. manual/unassociated items remain unchanged;
15. replacement path preserves canonical Character, Face parameter/effect state, geometry and one-bundle identity;
16. trial switching satisfies the P0-proved native Undo policy or is truthfully reported BLOCKED;
17. Tool utility-menu placement is proved if implemented, otherwise absence of supported host API is documented without hacks;
18. all prior P/W/WUX/R/Template-fidelity/UIUX/package gates remain green.

## Definition of done

The implementation pass is done only when the ordinary user can reason in the same order everywhere:

`Item -> what do I want to do -> Set -> action/configuration`

and the expression-specialist mode supports:

`double-click Voice -> preview that moment -> choose expression -> immediate safe result -> move to next Voice`.

A green build alone is not completion. Native behavior, narrow-layout evidence, package evidence and later real-user PSD hands-on acceptance remain separate gates.
